AI 활용 방안 — 컨텍스트 비용을 아끼는 전략

핵심 문제

AI에게 작업을 맡길 때마다 컨텍스트 비용이 누적된다. 작업이 진행 중일 때 계속 “끝났어?”라고 물어볼 때마다:

  1. 현재까지의 대화 맥락 전체가 다시 전송됨
  2. 토큰 사용량이 계속 증가함
  3. 비용이 불필요하게 늘어남

전략 1: 끝내고 기다려라고 말해라

“끝내고 기다려. 끝나면 하네스가 다시 불러.”

AI에게 작업을 맡긴 후, 진행 상황을 묻지 않는다. 작업이 완료되면 Hermes가 자동으로 알림을 보내기 때문에 굳이 물어볼 필요가 없다.

작동 원리

사용자: "이 작업 끝내줘"
    ↓
AI: 백그라운드에서 작업 시작
    ↓
사용자: 기다림 (물어보지 않음) ← 핵심
    ↓
작업 완료 → Hermes 자동 알림
    ↓
사용자: 결과 확인

비용 비교

방식컨텍스트 전송비용
매번 물어보기대화 맥락 × N번높음
기다렸다가 알림 받기완료 시 1회낮음

전략 2: 배치 작업으로 묶어서 요청

여러 작업을 개별적으로 요청하지 말고 한 번에 묶어서 요청.

  • ❌ “요약해줘” → “번역해줘” → “정리해줘” (컨텍스트 3회)
  • ✅ “요약하고 번역하고 정리해줘” (컨텍스트 1회)

전략 3: 새 세션에서 새 작업

Hermes는 대화가 길어지면 자동으로 컨텍스트를 압축하지만, 압축에도 비용이 든다.

  1. 새 작업은 새 세션에서 시작 (/new)
  2. 이전 결과는 위키에 저장 → 다음 세션에서는 링크만 참조
  3. 컨텍스트가 아닌 파일 시스템의 지식을 활용

전략 4: 스크립트 기반 자동화

반복 작업은 AI에게 매번 맡기지 말고 스크립트로 자동화.

  • ❌ 매번 “뉴스 수집해줘” → 매번 컨텍스트 비용
  • ✅ cron job으로 1시간마다 자동 수집 → 컨텍스트 비용 0

전략 5: 캐시 우선 실행 (Cache-Write First)

여러 에이전트가 동시에 돌아갈 때, 캐시 라이트를 먼저 실행한 후 나머지를 실행한다.

문제

여러 에이전트가 동시에 같은 컨텍스트를 참조하면:

  1. 각 에이전트가 독립적으로 전체 컨텍스트를 로드 → 중복 비용
  2. 캐시가 채워지기 전에 실행되면 캐시 효과 없음

해결: Cache-Write First 패턴

1단계: 첫 에이전트 실행 (Cache-Write)
   - 전체 컨텍스트 로드 → 캐시에 저장
   - 이 시점에서 캐시가 "워밍업"됨

2단계: 나머지 에이전트 실행 (Cache-Read)
   - 캐시에서 컨텍스트 로드 → 비용 절감
   - 캐시 히트로 토큰 비용 대폭 절감

비용 비교

방식컨텍스트 로드비용
동시 실행 (캐시 없음)전체 × N 에이전트최대
캐시 라이트 먼저 → 나머지 실행전체 1회 + 캐시 hit × (N-1)최소

실전 적용

  • delegate_task로 여러 서브에이전트를 실행할 때, 첫 에이전트가 완료된 후 나머지를 실행
  • cron job에서 첫 실행이 캐시를 채우고, 이후 실행은 캐시를 활용
  • Hermes의 context_from 기능으로 이전 작업 결과를 캐시처럼 활용

요약

전략효과
끝내고 기다려라고 말하기불필요한 폴링 비용 제거
배치 작업컨텍스트 재사용으로 비용 절감
새 세션에서 새 작업컨텍스트 압축 비용 회피
스크립트 자동화반복 작업 컨텍스트 비용 0
캐시 우선 실행여러 에이전트 동시 실행 시 캐시 히트로 비용 절감

핵심: AI에게 맡긴 작업은 끝날 때까지 기다려라. Hermes가 알려준다.

전략 6: 하네스 엔지니어링 (Harness Engineering)

핵심 개념

모델이 어떻게 행동하는지를 알고, 모델의 성향에 맞게 하네스를 구성하는 것이 베스트 퍼포먼스의 핵심이다.

데이터베이스 구축 원칙

데이터만 바뀌는 작업은 시스템 포트와 툴에 대한 디스크립션이 모두 동일해야 한다. 이렇게 하면:

  1. 모델이 한꺼번에 눌리게 행동하고 배움이 끝나면 하네스에 구축해버리면 됨
  2. 훨씬 더 비용을 세이브할 수 있음

멀티 에이전트 패턴

1. 멀티 에이전트 수행에 대한 툴을 정의
2. 첫 에이전트: Cache-Write 실행
3. 나머지 에이전트: Cache-Read로 패러럴 실행
4. 파레토적으로 구성만 해버리면 됨

모델 성향 파악 (3가지 방법)

모델이 나올 때마다 “봐야 되나?”라고 생각할 수 있지만, 모델이 어떻게 행동할 거니까 하네스를 이렇게 만들어야 한다는 것이 포인트이다.

테스트를 안 하고도 세 가지로 모델 성향을 볼 수 있음:

  1. 모델이 어떻게 변화하는지
  2. 그 정보들을 어떻게 얻는지
  3. 어떻게 수정해야 하는지

하네스 엔지니어의 역할과 한계

역할한계
모델 성향을 반영하여 베스트 퍼포먼스 유도모델이 바뀔 때마다 맞게 다 바꿔줘야 함
퍼블릭 정보를 듣고 모델 행동을 파악모델만 바꿨다고 달라지는 것을 잃어버릴 수 있음
프레임워크/SDK를 활용한 에이전트 구축소프트웨어 엔지니어링식 접근의 한계에 도달

퍼블릭에서 “이런 하네스 엔지니어링이 좋다더라”는 정보를 과정 없이 무조건 수용하지 말고, 모델이 어떻게 움직이는지 듣고 가는 것이 중요하다.

벤치마크에 대한 태도

  • 벤치마크를 볼 때 완벽하다고 생각하면 안 됨
  • 모델이 몰라도 되는 것도 있음
  • 모델에게 컨텍스트를 알게 해서 얻는 이점이 있음

레인 에이전트 (Lane Agent)의 중요성

서브 에이전트가 결과를 제대로 받는 게 중요해서 레인 에이전트가 한 번 더 하게 됨.

핵심 트레이드오프:

  • 비용을 아끼는 게 먼저인지
  • 결과를 더 로버스트하게 만드는 게 먼저인지

→ 이것은 유저가 판단해야 함
