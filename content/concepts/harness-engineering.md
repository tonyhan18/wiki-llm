# 하네스 엔지니어링 — 모델 성향에 맞는 AI 시스템 구축

## 핵심 개념

모델이 어떻게 행동하는지를 알고, **모델의 성향에 맞게 하네스를 구성**하는 것이 베스트 퍼포먼스의 핵심이다.

## 데이터베이스 구축 원칙

데이터만 바뀌는 작업은 **시스템 포트와 툴에 대한 디스크립션이 모두 동일**해야 한다.

1. 모델이 한꺼번에 눌리게 행동하고 배움이 끝나면 **하네스에 구축**해버리면 됨
2. 훨씬 더 비용을 세이브할 수 있음

## 멀티 에이전트 패턴

멀티 에이전트 수행에 대한 툴을 정의하고 **캐시 라이트 먼저**, 나머지를 **패러럴로 실행**할 수 있게 파레토적으로 구성만 해버리면 된다.

```
1. 멀티 에이전트 수행에 대한 툴을 정의
2. 첫 에이전트: Cache-Write 실행
3. 나머지 에이전트: Cache-Read로 패러럴 실행
4. 파레토적으로 구성만 해버리면 됨
```

## 모델 성향 파악 (3가지 방법)

모델이 나올 때마다 "봐야 되나?"라고 생각할 수 있지만, **모델이 어떻게 행동할 거니까 하네스를 이렇게 만들어야 한다**는 것이 포인트이다.

테스트를 안 하고도 세 가지로 모델 성향을 볼 수 있음:

1. 모델이 **어떻게 변화**하는지
2. 그 **정보들을 어떻게 얻**는지
3. **어떻게 수정**해야 하는지

## 하네스 엔지니어의 역할과 한계

| 역할 | 한계 |
|------|------|
| 모델 성향을 반영하여 베스트 퍼포먼스 유도 | 모델이 바뀔 때마다 맞게 다 바꿔줘야 함 |
| 퍼블릭 정보를 듣고 모델 행동을 파악 | 모델만 바꿨다고 달라지는 것을 잃어버릴 수 있음 |
| 프레임워크/SDK를 활용한 에이전트 구축 | 소프트웨어 엔지니어링식 접근의 한계에 도달 |

> 퍼블릭에서 "이런 하네스 엔지니어링이 좋다더라"는 정보를 **과정 없이 무조건 수용하지 말고**, 모델이 어떻게 움직이는지 듣고 가는 것이 중요하다.

## 벤치마크에 대한 태도

- 벤치마크를 볼 때 **완벽하다**고 생각하면 안 됨
- 모델이 몰라도 되는 것도 있음
- **모델에게 컨텍스트를 알게 해서 얻는 이점**이 있음

## 레인 에이전트 (Lane Agent)의 중요성

서브 에이전트가 결과를 **제대로 받는 게 중요**해서 레인 에이전트가 한 번 더 하게 됨.

핵심 트레이드오프:
- **비용을 아끼는 게 먼저인지**
- **결과를 더 로버스트하게 만드는 게 먼저인지**

→ 이것은 **유저가 판단**해야 함

## 에이전트 성향 파악 방법

에이전트를 만들 때 엔드포인트 LLM의 성향을 쉽게 파악할 수 있는 방법:
- 클로드 외에 일반적인 모델에 대해서는 잘 모를 수 있음
- 에이전트를 만들 때 **프레임워크를 SDK로 활용**하는 것도 좋은 방법
